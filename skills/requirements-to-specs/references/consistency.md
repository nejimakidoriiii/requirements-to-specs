# 整合性確認 — `<output_dir>/trace.md`

同一 REQ-ID の生成物を突き合わせ、3形式が同じ要求を検査していることを確認する。

## trace matrix

`<output_dir>/trace.md` に表を作る。分類表で true の形式のセルに、その REQ-ID を担う定義の名前を書く。false の形式は `—` を書く:

```markdown
| REQ-ID | Gherkin | Quint | Alloy | 判定 |
|--------|---------|-------|-------|------|
| REQ-001 | @REQ-001 未払い注文は発送できない | action ship, val noUnpaidShipment | — | 一致 |
| REQ-002 | — | — | fact REQ002_OneOwnerPerOrder | 一致 |
```

## 確認項目

各 REQ-ID の行について、true が2つ以上あるときに次の5項目を判定する。単一形式の行は「分類表の根拠コメントが妥当か」だけ確認する。

1. **語彙**: 同じ概念が3形式で同じ語幹か。Gherkin の「キャンセル済み」、Quint の `Cancelled`、Alloy の `sig Cancelled` が同じ概念を指すか。言い換えがあると追跡不能になる
2. **終端性**: ある形式で終端状態とされる状態（そこから出る遷移がない）が、別の形式で遷移先または実行可能アクションとして現れていないか
   - 例: Gherkin に「キャンセル済み注文を再開できる」という Scenario があるのに、Quint で `Cancelled` から出る遷移がなければ矛盾
3. **ガード**: 同じアクションの実行可否が一致しているか。Gherkin の When が成功する Scenario なのに、Quint の対応 action のガードが常に false になる、あるいはその逆、は矛盾
4. **多重度**: 件数の制約が一致しているか。Alloy の `lone`（0か1）に対して Gherkin が複数登録の手順を書いていないか
5. **対称性**: ある形式が REQ-ID について表現している制約は、残りの形式が前提としていないか。Gherkin の Then が前提とする観察結果（追跡番号の表示）に、Quint の状態遷移が到達できるか

## 矛盾の処置

矛盾は要求の曖昧さの兆候である。生成物を黙って修正して矛盾を隠さない。次の手順を取る:

1. trace.md の該当行の判定を「矛盾」とし、両形式の該当箇所を引用して記録する
2. パイプラインの最後に、REQ-ID・両形式の記述・どちらが正しいかの問いをユーザーに提示する
3. 回答を受けてから requirements.md・分類表・生成物を更新し、整合性確認をやり直す
