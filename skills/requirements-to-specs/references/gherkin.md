# Gherkin — `<output_dir>/gherkin/*.feature`

Gherkin は「利用者から何が観察できるか」を書く。利用者や外部システムが入力を与えて応答を受け取れる振る舞いが対象。外部から観察できない内部状態（テーブルのカラム、内部フラグの値そのもの）は書かない。

## REQ-ID の埋め込み

Scenario にタグを付ける:

```gherkin
@REQ-001
Scenario: 未払い注文は発送できない
```

1つの Scenario に複数の REQ-ID が関わるときはタグを列挙する（`@REQ-001 @REQ-007`）。

## 構文の要点

```gherkin
Feature: 注文の発送
  注文は支払い完了後にのみ発送できる。

  Background:
    Given 利用者がログインしている

  @REQ-001
  Scenario: 未払い注文は発送できない
    Given 未払いの注文がある
    When 利用者がその注文を発送しようとする
    Then 注文は発送されず、支払いを促すメッセージが表示される

  @REQ-004
  Scenario Outline: 支払い済み注文は発送できる
    Given 支払い済みの注文がある
    When 利用者がその注文を発送する
    Then 注文の発送が完了し、追跡番号が表示される

    Examples:
      | 支払い方法 |
      | クレジットカード |
      | 銀行振込 |
```

- `Given` = 前提の観察可能な状態、`When` = 1つのアクション、`Then` = 観察可能な応答
- 全 Scenario 共通の前提は `Background` に置く
- データの組み合わせだけで変わる同一テンプレートは `Scenario Outline` + `Examples` でまとめる

## 規約

- 1 Scenario につき振る舞いは1つ。複数の When-Then が要る場合は Scenario を分割する
- When は1つのアクションにする。2つの操作が必要な振る舞いは、その複合アクションに名前を付けて1ステップにする
- Then は観察可能な応答として書く: 画面の表示内容、エラーメッセージ、API の応答コード、送信される通知。「内部ステータスが shipped になる」は、そのまま書かず観察できる形（追跡番号の表示等）に書き換える
- Given に内部状態の設定手順（SQL、管理画面の操作手順）を書かない。前提状態を1文で宣言する
- 否定シナリオ（拒否、エラー）も REQ-ID が要求するなら必ず書く。正常系だけの Feature にしない

## 状態の語彙

要求に現れる状態名（未払い、支払い済み、発送済み）は、Quint の状態変数と同じ語幹になるようステップ文中で使う。整合性確認（`consistency.md`）で3形式の語彙が一致するか検査するため、独自の言い換えをしない。
